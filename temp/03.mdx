<Section num="01" id="intro" title="Mengapa EC2 Butuh Storage?" sub="Storage menentukan apakah data aman, cepat, bersama, atau sementara">

<p class="lead">
  Saat membuat EC2 instance, kita tidak hanya memilih CPU dan RAM, tetapi juga
  harus memilih tempat menyimpan data.
</p>

Bayangkan EC2 seperti laptop sewaan di cloud. Laptop itu butuh disk untuk sistem operasi, aplikasi, file konfigurasi, log, cache, database kecil, atau data sementara. Di AWS, pilihan storage untuk EC2 tidak hanya satu. Ada storage yang persisten, storage yang sangat cepat tetapi sementara, storage file bersama, dan storage khusus untuk workload tertentu.

<Figure>
  <EC2StorageFig01 />

    storage persisten, Instance Store untuk storage lokal sementara, EFS untuk
    file sharing Linux, dan FSx untuk file system terkelola khusus.
  </Fragment>
</Figure>

<CardGrid cols={2}>
  <Card>
    <h4>Block storage</h4>
    <p>
      Cocok seperti hard disk virtual untuk satu server. Contoh utama: Amazon
      EBS.
    </p>
  </Card>
  <Card>
    <h4>Temporary local storage</h4>
    <p>
      Cocok untuk cache dan data sementara dengan performa tinggi. Contoh: EC2
      Instance Store.
    </p>
  </Card>
  <Card>
    <h4>Shared file storage</h4>
    <p>
      Cocok untuk banyak EC2 yang perlu mengakses folder yang sama. Contoh:
      Amazon EFS.
    </p>
  </Card>
  <Card>
    <h4>Managed file system khusus</h4>
    <p>
      Cocok untuk kebutuhan Windows file share, Lustre, NetApp ONTAP, dan
      OpenZFS. Contoh: Amazon FSx.
    </p>
  </Card>
</CardGrid>

<Box variant="analogy" icon="🏠" label="Analogi rumah kontrakan">
  <p>
    EC2 adalah rumah kontrakan, EBS adalah lemari pribadi yang bisa dipindah ke
    rumah lain, Instance Store adalah meja kerja yang hilang saat rumah
    dikosongkan, EFS adalah gudang bersama, dan FSx adalah ruang kerja khusus
    dengan peralatan profesional.
  </p>
</Box>

<Section num="02" id="ebs-overview" title="Amazon EBS Overview" sub="Disk virtual persisten untuk EC2">

<p class="lead">
  Amazon Elastic Block Store, atau EBS, adalah block storage persisten yang
  biasa dipakai sebagai disk untuk EC2 instance.
</p>

EBS biasanya digunakan untuk root volume sistem operasi, data aplikasi, database, log penting, dan file yang harus tetap ada walaupun EC2 dihentikan lalu dijalankan kembali. Karena sifatnya block storage, EBS terasa seperti hard disk atau SSD yang terpasang ke server.

EBS bersifat terikat ke Availability Zone. Artinya, volume EBS di satu AZ hanya bisa dipasang ke EC2 yang berada di AZ yang sama. Untuk memindahkan data antar AZ atau Region, biasanya kita memakai snapshot.

<CardGrid cols={3}>
  <Card>
    <h4>Persisten</h4>
    <p>
      Data tetap ada walaupun instance dihentikan, selama volume tidak dihapus.
    </p>
  </Card>
  <Card>
    <h4>Attach dan detach</h4>
    <p>
      Volume bisa dilepas dari satu instance lalu dipasang ke instance lain di
      AZ yang sama.
    </p>
  </Card>
  <Card>
    <h4>Ukuran bisa diubah</h4>
    <p>
      Kapasitas dan performa volume dapat disesuaikan sesuai kebutuhan workload.
    </p>
  </Card>
</CardGrid>

<Section num="03" id="ebs-multi-attach" title="EBS Multi-Attach" sub="Satu volume EBS ke beberapa instance dalam AZ yang sama">

<p class="lead">
  EBS Multi-Attach memungkinkan satu volume EBS tertentu dipasang ke beberapa
  EC2 instance dalam Availability Zone yang sama.
</p>

Fitur ini bukan untuk semua jenis volume. Multi-Attach digunakan pada volume Provisioned IOPS SSD tertentu, seperti <code>io1</code> atau <code>io2</code>. Setiap instance yang terpasang memiliki akses baca dan tulis ke volume tersebut, sehingga aplikasi harus benar-benar mampu menangani akses bersamaan.

<Box variant="warn" icon="⚠️" label="Bukan pengganti EFS">
  <p>
    Multi-Attach bukan file system sharing otomatis. Jika beberapa server
    menulis ke volume yang sama tanpa koordinasi, data bisa rusak. Gunakan file
    system atau aplikasi cluster-aware yang sesuai.
  </p>
</Box>

<CardGrid cols={2}>
  <Card>
    <h4>Kapan berguna?</h4>
    <p>
      Saat aplikasi high availability membutuhkan block storage bersama dan
      aplikasi tersebut memang dirancang untuk akses concurrent.
    </p>
  </Card>
  <Card>
    <h4>Kapan tidak cocok?</h4>
    <p>
      Untuk sekadar berbagi folder antar server biasa. Untuk kebutuhan itu, EFS
      biasanya lebih sederhana.
    </p>
  </Card>
</CardGrid>

</Section>

<Section num="04" id="ebs-hands-on" title="EBS Hands On" sub="Alur praktik membuat, memasang, dan memakai volume">

<p class="lead">
  Dalam praktik dasar, kita membuat volume EBS, memasangnya ke EC2, lalu
  menyiapkan file system agar bisa digunakan oleh sistem operasi.
</p>

<Steps>
  <Step>
    <b>Buat volume</b>
    <p>
      Buka layanan EC2, pilih menu Volumes, lalu buat EBS volume dengan ukuran,
      tipe, dan Availability Zone yang sama dengan instance target.
    </p>
  </Step>
  <Step>
    <b>Attach ke instance</b>
    <p>
      Pilih volume, gunakan aksi Attach volume, lalu pilih EC2 instance yang
      berada di AZ yang sama.
    </p>
  </Step>
  <Step>
    <b>Siapkan di sistem operasi</b>
    <p>
      Masuk ke instance, cek device baru, buat file system jika masih kosong,
      lalu mount ke folder tertentu.
    </p>
  </Step>
  <Step>
    <b>Uji penyimpanan</b>
    <p>
      Buat file percobaan di folder mount, lalu pastikan data tetap ada setelah
      instance dihentikan dan dijalankan kembali.
    </p>
  </Step>
</Steps>

<h3>Contoh alur Linux sederhana</h3>

<pre>
  <code>
    lsblk sudo mkfs -t xfs /dev/xvdf sudo mkdir /data sudo mount /dev/xvdf /data
    df -h
  </code>
</pre>

<Box variant="warn" icon="🧯" label="Hati-hati format volume">
  <p>
    Perintah <code>mkfs</code> akan membuat file system baru. Jangan jalankan
    pada volume yang sudah berisi data penting.
  </p>
</Box>

</Section>

<Section num="05" id="snapshot-ami" title="EBS Snapshot dan AMI" sub="Backup volume dan template instance">

<p class="lead">
  EBS snapshot adalah backup point-in-time dari volume EBS, sedangkan AMI adalah
  template untuk meluncurkan EC2 instance baru.
</p>

Snapshot membantu menyimpan salinan data volume. Snapshot dapat dipakai untuk membuat volume baru, memulihkan data, atau menyalin data ke Region lain. Dalam praktik AWS, snapshot EBS disimpan di belakang layar menggunakan Amazon S3, tetapi kita mengelolanya melalui fitur EBS Snapshot, bukan sebagai bucket S3 biasa.

AMI, atau Amazon Machine Image, adalah paket template yang berisi informasi untuk membuat instance baru. AMI biasanya mencakup sistem operasi, konfigurasi, aplikasi yang sudah dipasang, dan referensi snapshot root volume.

<Figure>
  <EC2StorageFig02 />
  <Fragment slot="caption">
    <b>Gambar 2.</b> Hubungan sederhana antara EC2, EBS volume, snapshot, AMI,
    dan instance baru.
  </Fragment>
</Figure>

<CardGrid cols={2}>
  <Card>
    <h4>Snapshot</h4>
    <p>Fokus pada backup volume. Cocok untuk recovery dan duplikasi storage.</p>
  </Card>
  <Card>
    <h4>AMI</h4>
    <p>
      Fokus pada template server. Cocok untuk membuat banyak EC2 dengan
      konfigurasi seragam.
    </p>
  </Card>
</CardGrid>

<Steps>
  <Step>
    <b>Buat snapshot</b>
    <p>Pilih volume EBS, lalu buat snapshot sebagai backup point-in-time.</p>
  </Step>
  <Step>
    <b>Buat volume baru</b>
    <p>
      Gunakan snapshot untuk membuat EBS volume baru, misalnya untuk restore.
    </p>
  </Step>
  <Step>
    <b>Buat AMI</b>
    <p>
      Dari EC2 instance yang sudah dikonfigurasi, buat AMI agar konfigurasi bisa
      dipakai ulang.
    </p>
  </Step>
  <Step>
    <b>Launch instance baru</b>
    <p>
      Pakai AMI tersebut untuk meluncurkan EC2 baru dengan konfigurasi yang
      mirip.
    </p>
  </Step>
</Steps>

<Box variant="exam" icon="🎯" label="Tips ujian">
  <p>
    Jika soal bertanya cara membuat banyak instance dengan konfigurasi sama,
    jawabannya sering AMI. Jika soal bertanya backup volume EBS, jawabannya
    snapshot.
  </p>
</Box>

</Section>

<Section num="06" id="image-builder" title="EC2 Image Builder" sub="Membuat dan merawat image secara otomatis">

<p class="lead">
  EC2 Image Builder membantu membuat, menguji, dan memperbarui image server
  secara otomatis.
</p>

Tanpa Image Builder, tim sering membuat AMI manual: launch instance, install package, patch sistem, konfigurasi aplikasi, lalu buat AMI. Cara manual bisa berulang, rawan lupa, dan sulit diaudit. Image Builder membuat proses ini lebih rapi melalui pipeline.

<CardGrid cols={3}>
  <Card>
    <h4>Build</h4>
    <p>Membuat image dari base image dan komponen yang ditentukan.</p>
  </Card>
  <Card>
    <h4>Test</h4>
    <p>
      Menjalankan pengujian agar image tidak langsung dipakai dalam kondisi
      rusak.
    </p>
  </Card>
  <Card>
    <h4>Distribute</h4>
    <p>Mendistribusikan image ke akun atau Region yang dibutuhkan.</p>
  </Card>
</CardGrid>

<Box variant="analogy" icon="🏭" label="Analogi pabrik roti">
  <p>
    AMI manual seperti membuat roti satu per satu di dapur. EC2 Image Builder
    seperti pabrik kecil dengan resep, pengecekan kualitas, dan pengemasan
    otomatis.
  </p>
</Box>

</Section>

<Section num="07" id="instance-store" title="EC2 Instance Store" sub="Storage lokal cepat tetapi sementara">

<p class="lead">
  EC2 Instance Store adalah storage block sementara yang secara fisik terpasang
  pada host tempat EC2 berjalan.
</p>

Instance Store biasanya sangat cepat karena dekat dengan host fisik. Namun data di dalamnya tidak persisten seperti EBS. Data dapat hilang ketika instance dihentikan, di-terminate, atau host fisik bermasalah. Karena itu, Instance Store cocok untuk data sementara, bukan data utama yang harus aman.

<CardGrid cols={2}>
  <Card>
    <h4>Cocok</h4>
    <p>
      Cache, buffer, temporary files, scratch data, dan workload yang bisa
      membangun ulang data dari sumber lain.
    </p>
  </Card>
  <Card>
    <h4>Tidak cocok</h4>
    <p>
      Database utama, file penting, backup, atau data yang harus tetap ada
      setelah instance berhenti.
    </p>
  </Card>
</CardGrid>

<Box variant="warn" icon="⚠️" label="Ingat kata kunci ujian">
  <p>
    Jika soal menyebut storage sangat cepat tetapi ephemeral atau temporary,
    pikirkan EC2 Instance Store. Jika data harus persisten, pikirkan EBS, EFS,
    atau FSx.
  </p>
</Box>

</Section>

<Section num="08" id="efs-overview" title="Amazon EFS Overview" sub="File system bersama untuk banyak EC2 Linux">

<p class="lead">
  Amazon Elastic File System, atau EFS, adalah file storage terkelola yang dapat
  dipakai bersama oleh banyak EC2 instance Linux.
</p>

EFS cocok ketika beberapa server perlu membaca dan menulis file yang sama. Contohnya aplikasi web yang berjalan di beberapa EC2 instance tetapi perlu folder upload bersama. EFS bersifat elastis, sehingga kapasitasnya dapat bertambah dan berkurang sesuai jumlah file yang disimpan.

<CardGrid cols={3}>
  <Card>
    <h4>Shared</h4>
    <p>Banyak EC2 dapat mount file system yang sama.</p>
  </Card>
  <Card>
    <h4>Elastic</h4>
    <p>
      Kapasitas mengikuti data yang disimpan, tanpa perlu menentukan ukuran awal
      seperti EBS.
    </p>
  </Card>
  <Card>
    <h4>Regional</h4>
    <p>Dapat diakses melalui mount target di beberapa Availability Zone.</p>
  </Card>
</CardGrid>

<Section num="09" id="shared-responsibility" title="Shared Responsibility untuk EC2 Storage" sub="AWS menjaga cloud, kita menjaga konfigurasi dan data">

<p class="lead">
  Dalam model tanggung jawab bersama, AWS bertanggung jawab atas keamanan
  infrastruktur cloud, sedangkan kita bertanggung jawab atas konfigurasi, akses,
  dan data yang kita simpan.
</p>

Untuk EC2 storage, ini berarti AWS mengelola fasilitas fisik, hardware, dan infrastruktur layanan. Namun pengguna tetap bertanggung jawab untuk memilih konfigurasi yang aman, mengatur izin, mengenkripsi data bila dibutuhkan, melakukan backup, patching sistem operasi, dan menghapus data yang tidak diperlukan.

<CardGrid cols={2}>
  <Card>
    <h4>Tanggung jawab AWS</h4>
    <p>
      Keamanan data center, perangkat keras, jaringan global, dan infrastruktur
      dasar layanan AWS.
    </p>
  </Card>
  <Card>
    <h4>Tanggung jawab pengguna</h4>
    <p>
      IAM, security group, enkripsi, backup, patch OS, izin file, dan lifecycle
      data.
    </p>
  </Card>
</CardGrid>

<Box variant="exam" icon="🎯" label="Tips ujian">
  <p>
    Untuk EC2, pengguna memiliki tanggung jawab lebih besar dibanding layanan
    managed penuh. Misalnya, patch sistem operasi di EC2 adalah tanggung jawab
    pengguna.
  </p>
</Box>

</Section>

<Section num="10" id="fsx-overview" title="Amazon FSx Overview" sub="File system terkelola untuk kebutuhan khusus">

<p class="lead">
  Amazon FSx adalah keluarga layanan file system terkelola untuk kebutuhan yang
  lebih spesifik daripada EFS.
</p>

Jika EFS terasa seperti file sharing Linux yang sederhana dan elastis, FSx adalah pilihan ketika workload membutuhkan file system tertentu dengan fitur khusus. AWS menyediakan beberapa varian FSx, seperti FSx for Windows File Server, FSx for Lustre, FSx for NetApp ONTAP, dan FSx for OpenZFS.

  <p>
    EFS adalah pilihan file sharing Linux yang umum. FSx adalah pilihan ketika
    soal menyebut teknologi file system tertentu, seperti Windows SMB, Lustre,
    NetApp ONTAP, atau OpenZFS.
  </p>
</Box>

</Section>

<Section num="12" id="ringkasan" title="Ringkasan & Tips Ujian" sub="Poin yang paling sering muncul di CLF-C02 dan SAA-C03">

<p class="lead">
  EC2 storage terlihat banyak, tetapi pola soalnya biasanya berputar pada
  persistensi, sharing, performa, dan tanggung jawab keamanan.
</p>

<Recap title="Poin Penting">
  <ul>
    <li>
      <strong>EBS</strong> adalah block storage persisten untuk EC2, umum
      dipakai sebagai boot volume dan data volume.
    </li>
    <li>
      <strong>EBS volume</strong> berada dalam satu Availability Zone dan
      biasanya dipasang ke EC2 di AZ yang sama.
    </li>
    <li>
      <strong>EBS Multi-Attach</strong> memungkinkan volume tertentu dipasang ke
      beberapa EC2 dalam AZ yang sama, tetapi aplikasi harus menangani akses
      tulis bersamaan.
    </li>
    <li>
      <strong>EBS Snapshot</strong> adalah backup point-in-time dari volume EBS.
    </li>
    <li>
      <strong>AMI</strong> adalah template untuk membuat EC2 instance baru
      dengan konfigurasi yang sudah disiapkan.
    </li>
    <li>
      <strong>EC2 Image Builder</strong> membantu otomatisasi pembuatan,
      pengujian, dan distribusi image.
    </li>
    <li>
      <strong>Instance Store</strong> cepat tetapi sementara, cocok untuk cache
      dan temporary data.
    </li>
    <li>
      <strong>EFS</strong> adalah file storage bersama untuk banyak EC2 Linux.
    </li>
    <li>
      <strong>FSx</strong> adalah keluarga file system terkelola untuk kebutuhan
      khusus seperti Windows File Server, Lustre, NetApp ONTAP, dan OpenZFS.
    </li>
    <li>
      <strong>Shared Responsibility</strong> berarti AWS menjaga infrastruktur
      cloud, sedangkan pengguna menjaga konfigurasi, akses, backup, enkripsi,
      dan data.
    </li>
  </ul>
</Recap>

    <strong>Windows file share</strong> berarti FSx for Windows File Server.{" "}
    <strong>Backup EBS</strong> berarti snapshot. <strong>Template EC2</strong>{" "}
    berarti AMI.
  </p>
